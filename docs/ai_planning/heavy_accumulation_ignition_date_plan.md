# 主力吸籌點火起算日演算法與報表維度升級規劃

## 1. 核心目標
解決「60 天季線模型中，起算日全數顯示 6/3，無法反映主力（如川湖+凱基三多）在 7 月才真正大舉建倉爆發之真實情況」問題，並確立以 **「20% 自適應總部位累積門檻」** 作為核心參數。

## 2. 為什麼不採用「固定金額（如 500 萬元）」？
1. **高低價股股價差距巨大**：
   - 川湖 (2059) 一張 1,300 ~ 1,500 萬元，500 萬連 1 張都不到，散戶買 1 張就會誤觸發點火。
   - 30 元小型股一張 3 萬元，500 萬已是 160 張的大單。
2. **大戶與小主力資金懸殊**：
   - 凱基三多在川湖累計買超數十億元，500 萬佔總量不到 0.5%，屬於日常試單雜訊。
3. **結論**：必須採用 **「自適應總部位比例（Adaptive Ratio）」** 才能不受股價高低與資金規模干擾。

## 3. 重要核心參數：點火確認門檻比例 (ignition_threshold_ratio = 0.20)
* **參數定義**：`ignition_threshold_ratio = 0.20`（預設 20%）。
* **理論依據**：
  - **主力建倉生命週期**：`[0%~10%] 潛伏試單期` ──> `[20%~70%] 正式加碼點火期` ──> `[70%~100%] 鎖碼拉抬期`。
  - **雜訊過濾與時效性黃金平衡點**：
    - 設 5%~10%：會誤抓 6 月份零星試單。
    - 設 50%：發動點會延後至股價漲至半山腰。
    - **20% 正好落在主力連續大買脫離底部的第 2~4 天**，精準抓到初升段。

## 4. 系統實作架構

### 4.1 DuckDB 每日累計曲線查詢
```sql
ignition_dates AS (
    SELECT
        d.symbol,
        d.broker_id,
        MIN(d.trade_date) AS ignition_date
    FROM daily_cum d
    JOIN summary_per_pair s ON d.symbol = s.symbol AND d.broker_id = s.broker_id
    WHERE (
        -- ★ 自適應判定：累計淨買超金額 >= 該分點最終總買超部位的 20%
        d.cum_net_amt >= (s.total_net_amt_k * {ignition_threshold_ratio})
    )
    GROUP BY d.symbol, d.broker_id
)
```

### 4.2 吃貨歷時與狀態標籤
- **吃貨歷時 (天)**：從 `ignition_date` 至 `last_date` 之日曆天數。
- **狀態標籤**：
  - `🚀 剛點火`：歷時 $\le 7$ 天或進出 $\le 3$ 天
  - `🔥 連續吸籌`：買超天數 $\ge 3$ 且純度 $\ge 75\%$
  - `🎯 絕對鎖碼`：純度 $\ge 85\%$
  - `💰 億級重押`：淨買超金額 $\ge 1.0$ 億元
